The transactional email API sends one email to one person from your server code, such as a welcome email, a signup confirmation, or a password reset. You call `posthog.emails.send` on the PostHog client that you already use, in Node.js or in Python. PostHog sends the email through Workflows and records delivery and engagement on the recipient's person.

<CalloutBox icon="IconInfo" title="The transactional email API is in beta" type="fyi">

The API is in beta, and PostHog enables it per project. To use it, [ask us in-app](https://app.posthog.com/#panel=support%3Afeedback%3A%3Alow%3Atrue) to enable it for your project. Until then, the upload route, the send routes, and the change request route answer `404` with the code [`not_found`](#not_found). Routes, fields, and messages can change while the API is in beta.

</CalloutBox>

## How it works

A send takes one of two forms:

- **A template made in PostHog**, sent by its `template_id`, with `template_data` for its `{{ variables.* }}` placeholders. Edit the template in PostHog, and your code keeps sending it.
- **An email from your code**, named by a `template_key` that you choose, such as `password-reset`, with its `subject`, and `html` or `text`. The key groups the email's logs, metrics, and status in PostHog. This form has two cases:
  - **Rendered content.** Your code renders the email for one recipient, for example with React Email. PostHog sends it as it is and doesn't store it as a template.
  - **A local template.** Your code holds a template with `{{ variables.* }}` placeholders and sends it with `template_data`. The SDK uploads the template to PostHog on its first send and whenever its content changes. You never call an upload.

A send can't mix the two forms. Pass `template_id`, or `template_key` with the content.

## Before you start

1. **Verify a sender.** [Set up the email channel](/docs/workflows/configure-channels) with a domain that you own, and make the verified sender your project's default sender: click **Make default** next to the sender in the email channel settings. An email from your code goes out from the default sender unless the send sets `from`.
2. **Create a project secret API key.** Create a [project secret API key](/docs/api/project-secret-api-keys) (it starts with `phs_`) with the `hog_flow:write` scope, which also lets it [read an email's status](#read-an-emails-status). Keep it on your server, for example in the `POSTHOG_PROJECT_SECRET_API_KEY` environment variable. Never put it in browser or mobile code.
3. **Ask for access.** The API must be enabled for your project. See the beta note above.

A project secret API key can only upload templates, send them, and read the status of an email. It can't read, edit, or delete templates. To call the other template routes, such as [adoption](#adopt-a-template-made-in-posthog), use a [personal API key](/docs/api/personal-api-keys) with `hog_flow:write`. A [change request](#run-with-posthog-code) needs `hog_flow:read` and `task:write` instead.

Project secret API keys are in beta and may not be available in your organization yet. Until they are, the upload and send routes also accept a personal API key with `hog_flow:write` and editor access to Workflows. With a personal API key, put the project ID in the URL instead of `@current`. The SDKs always call `@current`, so use them with a project secret API key.

## Set up the client

Email is a namespace on the PostHog client, `posthog.emails`. Give the client your project secret API key:

<MultiLanguage>

```js
import { PostHog } from 'posthog-node'

const posthog = new PostHog('<ph_project_token>', {
    host: '<ph_client_api_host>',
    secretKey: process.env.POSTHOG_PROJECT_SECRET_API_KEY,
})
```

```python
import os
from posthog import Posthog

posthog = Posthog(
    '<ph_project_token>',
    host='<ph_client_api_host>',
    secret_key=os.environ['POSTHOG_PROJECT_SECRET_API_KEY'],
)
```

</MultiLanguage>

| Node.js | Python | Description |
| --- | --- | --- |
| `secretKey` | `secret_key` | A project secret API key with `hog_flow:write`. Without it, a send fails with [`missing_secret_key`](#missing_secret_key). |
| `appHost` | `app_host` | The PostHog app host that receives the send, such as `https://posthog.example.com` for a self-hosted instance. See below. |
| `maxRetries` | `max_retries` | How often the SDK retries a failed send. Defaults to `2`, so a send makes at most 3 attempts. `0` turns retries off. A send can override it. See [retries](#what-the-sdks-retry). |

**The app host.** Sends go to the PostHog app, not to the ingestion host that events use. When `host` is PostHog Cloud (`us.i.posthog.com`, `us.posthog.com`, `eu.i.posthog.com`, or `eu.posthog.com`), the SDK knows the app host. Any other `host` can be a reverse proxy for events, and the secret key must never go there. So for any other host, set `appHost` (`app_host` in Python). Without it, a send fails with [`missing_app_host`](#missing_app_host) and sends no request.

In Node.js, `secretKey` also turns on [local evaluation](/docs/feature-flags/local-evaluation) of Feature Flags, which needs the `feature_flag:read` scope. If the key only has `hog_flow:write`, set `enableLocalEvaluation: false`.

In Python, `AsyncPosthog` has the same `emails` namespace, with an awaitable `send`.

## Send a template made in PostHog

Pass the template's ID as `template_id`, and the values for its placeholders as `template_data`. Copy the ID from the template's **API** tab in Workflows. The template must be transactional.

<MultiLanguage>

```js
const { data, error } = await posthog.emails.send({
    to: 'jane@example.com',
    distinctId: user.id,
    templateId: '01a14631-40b7-0000-4dfd-60cd5a2e12ad',
    templateData: { first_name: 'Jane', login_url: 'https://hedgebox.example.com/login' },
})

if (error) {
    console.error(error.name, error.code, error.message, error.docsUrl)
}
```

```python
from posthog.emails import EmailError

try:
    result = posthog.emails.send(
        to='jane@example.com',
        distinct_id=user.id,
        template_id='01a14631-40b7-0000-4dfd-60cd5a2e12ad',
        template_data={'first_name': 'Jane', 'login_url': 'https://hedgebox.example.com/login'},
    )
except EmailError as error:
    print(error.name, error.code, error.message, error.docs_url)
```

</MultiLanguage>

- `to` is one recipient's email address.
- `distinctId` (`distinct_id` in Python) is the recipient's distinct ID in your app. [Always pass it](#always-pass-distinct_id).
- `templateData` (`template_data`) fills the template's `{{ variables.* }}` placeholders. A send never reads person properties, so pass every value the email needs.
- Node.js returns `{ data, error }` and never throws for an API or network error. Python returns the result and raises an `EmailError`. See [results and errors](#results-and-errors-in-the-sdks).

## Send an email from your code

Name the email with `template_key`, and pass its `subject` and its `html`, `text`, or both. A key has only letters, digits, hyphens (`-`), and underscores (`_`), with at most 400 characters. Keep the key the same for one kind of email: PostHog groups the email's metrics, logs, and status by its key, in every project.

### Send rendered content

Render the email in your code, then send the result. PostHog sends the content as it is. It doesn't fill in placeholders, and it doesn't store the content as a template.

<MultiLanguage>

```js
const { data, error } = await posthog.emails.send({
    to: 'jane@example.com',
    distinctId: user.id,
    templateKey: 'password-reset',
    subject: 'Reset your password',
    html: `<p>Hi Jane,</p><p><a href="${resetUrl}">Reset your password</a>. The link works for one hour.</p>`,
    from: 'Hedgebox <security@example.com>',
})
```

```python
result = posthog.emails.send(
    to='jane@example.com',
    distinct_id=user.id,
    template_key='password-reset',
    subject='Reset your password',
    html=f'<p>Hi Jane,</p><p><a href="{reset_url}">Reset your password</a>. The link works for one hour.</p>',
    from_='Hedgebox <security@example.com>',
)
```

</MultiLanguage>

When you send `html` without `text`, PostHog derives the plain-text part from the HTML. When the HTML has no text to derive, such as an email that is only an image, the email goes out without a plain-text part.

### Send a React Email component

The SDKs have no React helper. Render the component to HTML with [React Email](https://react.email) in your code, then send the HTML as rendered content:

```jsx
import { render } from '@react-email/render'
import { PasswordReset } from './emails/PasswordReset'

const { data, error } = await posthog.emails.send({
    to: 'jane@example.com',
    distinctId: user.id,
    templateKey: 'password-reset',
    subject: 'Reset your password',
    html: await render(<PasswordReset url={resetUrl} />),
})
```

Your components stay as they are. PostHog derives the text part from the rendered HTML.

### Send a local template

A local template keeps the email in your code, with `{{ variables.* }}` placeholders in the subject and the body. Send it with `template_data`, and PostHog fills in the values:

<MultiLanguage>

```js
import { readFileSync } from 'node:fs'

const welcomeHtml = readFileSync(new URL('./emails/welcome.html', import.meta.url), 'utf8')

const { data, error } = await posthog.emails.send({
    to: 'jane@example.com',
    distinctId: user.id,
    templateKey: 'welcome',
    subject: 'Welcome to Hedgebox, {{ variables.first_name }}',
    html: welcomeHtml,
    templateData: { first_name: 'Jane', login_url: 'https://hedgebox.example.com/login' },
})
```

```python
from pathlib import Path

welcome_html = (Path(__file__).parent / 'emails' / 'welcome.html').read_text()

result = posthog.emails.send(
    to='jane@example.com',
    distinct_id=user.id,
    template_key='welcome',
    subject='Welcome to Hedgebox, {{ variables.first_name }}',
    html=welcome_html,
    template_data={'first_name': 'Jane', 'login_url': 'https://hedgebox.example.com/login'},
)
```

</MultiLanguage>

`template_data` is what makes the send a local template. Without it, the same call sends rendered content, and the placeholders go out as written.

The template uses [Liquid](https://shopify.github.io/liquid/). It reads only the values of the send, as `{{ variables.<name> }}`. PostHog attaches the person to the send for attribution, but the template can't read `{{ person.properties.* }}`.

#### How a local template stays in sync

Your code is the source of truth. On every send, the SDK computes the template's [content hash](#content-hash) and sends the key and the hash:

- **PostHog holds this content.** The email goes out. This is one request.
- **PostHog doesn't hold this content**, because the key is new or you changed the template. PostHog answers [`template_outdated`](#template_outdated) and queues nothing. The SDK uploads the template under its key and sends again once, with the same [idempotency key](#idempotency). This is three requests.
- **Newer content replaced this content.** The email goes out with the newer content, and the result has a [`template_superseded`](#template_superseded) warning. The SDK doesn't upload. It logs the warning once.

So you don't need an upload step or a deploy step: the first send of a changed template publishes the change. The uploaded template is [managed by code](#templates-managed-by-code), so nobody can edit it in PostHog.

The SDK's upload refuses to overwrite a template that people edit in PostHog. When the key names such a template, a send that needs an upload fails with [`template_edited_in_posthog`](#template_edited_in_posthog) and sends nothing.

#### Rolling deploys

During a rolling deploy, your old instances and your new instances run at the same time, each with its own copy of the template. An old instance can't bring back content from any of the last 100 publishes:

- PostHog remembers the last 100 content hashes it published. An older hash counts as never published, so a template older than that uploads again.
- When a send carries one of the remembered hashes, PostHog sends the current content and adds the [`template_superseded`](#template_superseded) warning. Nothing is uploaded or reverted.
- The SDK's upload sets `if_not_superseded`, so it never publishes content that one of the last 100 publishes replaced. See [automatic uploads](#automatic-uploads-and-if_not_superseded).

Two side effects to know about:

- In development, when you change a template back to an earlier version, a send doesn't upload it, because PostHog published that content before. The warning tells you to upload it on purpose.
- When two people share one project with different local copies of a template, each sees the other's content as newer. Use one project per person, or upload explicitly.

To publish content that newer content replaced, such as when you roll back a release, upload it with the [upload route](#upload-a-template-by-key), without `if_not_superseded`. An upload that you make on purpose always publishes.

### Set the sender

| Node.js | Python | Description |
| --- | --- | --- |
| `from` | `from_` | The sender, as `security@example.com` or `Hedgebox <security@example.com>`, on a domain that the project verified. Without it, rendered content goes out from the project's default sender, and a local template from its template's sender. A sender that no verified sender of the project can send from fails with [`sender_not_allowed`](#sender_not_allowed). Without `from` and without a default sender, the send fails with [`sender_not_verified`](#sender_not_verified). |
| `replyTo` | `reply_to` | One address, or a list of up to 10 addresses, that replies go to. |

Python names the sender `from_`, because `from` is a Python keyword. `from` and `reply_to` only go with `template_key`. A template made in PostHog uses its own sender.

### Add copies, headers, tags, and attachments

An email from your code can carry copies, custom headers, tags, and files. Rendered content and local templates take them both:

<MultiLanguage>

```js
const { data, error } = await posthog.emails.send({
    to: 'jane@example.com',
    distinctId: user.id,
    templateKey: 'order-receipt',
    subject: 'Your Hedgebox receipt',
    html: receiptHtml,
    bcc: 'records@example.com',
    headers: { 'X-Entity-Ref-ID': 'order-123' },
    tags: [{ name: 'category', value: 'receipt' }],
    attachments: [{ filename: 'receipt.pdf', content: receiptPdf, contentType: 'application/pdf' }],
})
```

```python
result = posthog.emails.send(
    to='jane@example.com',
    distinct_id=user.id,
    template_key='order-receipt',
    subject='Your Hedgebox receipt',
    html=receipt_html,
    bcc='records@example.com',
    headers={'X-Entity-Ref-ID': 'order-123'},
    tags=[{'name': 'category', 'value': 'receipt'}],
    attachments=[{'filename': 'receipt.pdf', 'content': receipt_pdf, 'content_type': 'application/pdf'}],
)
```

</MultiLanguage>

| Node.js | Python | Description |
| --- | --- | --- |
| `cc` | `cc` | One address, or a list of up to 10, that get a visible copy. Use bare addresses, such as `jane@example.com`, without a display name. |
| `bcc` | `bcc` | One address, or a list of up to 10, that get a hidden copy. The other recipients never see them. |
| `headers` | `headers` | Up to 10 custom headers, such as `{ "X-Entity-Ref-ID": "order-123" }`. |
| `tags` | `tags` | Up to 10 `{ name, value }` pairs. PostHog adds them to the email's [engagement events](#engagement-capture) as `$email_tags`. |
| `attachments` | `attachments` | Up to 10 files, with at most 512 KB in total after decoding. Each file is `{ filename, content, contentType?, contentId? }` (`content_type` and `content_id` in Python). `content` is a `Buffer` or a Base64 string in Node.js, and `bytes` in Python. |

- **Headers.** PostHog sets some headers itself and refuses them in `headers`: `From`, `To`, `Cc`, `Bcc`, `Reply-To`, `Subject`, `Date`, `Message-ID`, `MIME-Version`, `Sender`, `Return-Path`, `Auto-Submitted`, and any `Content-*`, `X-PostHog-*`, or `X-SES-*` header. A header name has no spaces or colons, and a value is printable ASCII on one line. Header names ignore case, so set each name once.
- **Tags.** A tag name and a value use only ASCII letters, numbers, `_`, and `-`. Names that start with `ph_` are PostHog's. Each name can appear once.
- **Attachments.** Mailbox providers block some file types, such as `.exe`, and PostHog refuses them. A file name has no path and no line breaks. To show a file inline, give it a `contentId` (`content_id`), such as `logo`, and reference it in the HTML as `<img src="cid:logo">`. Send a link instead of a larger file.
- **Suppressed addresses.** When the `to` address, a `cc`, or a `bcc` address is suppressed, PostHog sends nothing and answers [`recipient_suppressed`](#recipient_suppressed). Every address counts as a recipient for the project's sending limits.

A template made in PostHog sends with its own settings, so a send by `template_id` takes none of these fields. A field that breaks a rule fails with [`invalid_request`](#invalid_request), and `field` names it, such as `tags__0__name`.

## Always pass `distinct_id`

Pass `distinctId` (`distinct_id` in Python) on every send, with the ID your app already uses for the user in PostHog. PostHog captures the email's [engagement events](/docs/workflows/engagement-events) on that person, next to their product events.

Without it, PostHog uses the recipient's email address as the distinct ID. The events then land on a separate person keyed by the address, not on your app's user.

The SDKs never take the recipient from the current request context. An invite that an admin sends lands on the invited person, not on the admin's timeline.

## What a successful send means

A successful send answers `202`. It means PostHog stored the send in its queue for delivery. It doesn't mean that the email provider accepted the email, or that the email was delivered.

PostHog runs the checks that would stop the email before it answers. A send to a suppressed address, from a sender that isn't verified, or from a paused template fails with an error that says why and how to fix it, instead of a `202` and a skipped email. Each check has a code in [errors](#errors).

The result carries the ID of the queued send, and any warnings:

- **Node.js:** `data` is `{ id, warnings }`. Each warning is `{ code, message, fix }`.
- **Python:** the result has `id`, `replayed`, and `warnings`. Each warning has `code`, `message`, and `fix`.

The SDKs log each warning once through the client's logger. They capture no event for a send: the send and its engagement events come from PostHog, so nothing is counted twice.

## Idempotency

Every send carries an idempotency key, so a retry doesn't send a second email.

- Pass your own key as `idempotencyKey` (`idempotency_key` in Python). When you pass none, the SDK makes a random UUID for the send, and uses it for each of its retries.
- A key has 1 to 255 visible ASCII characters, with no spaces. A wrong key fails with [`invalid_idempotency_key`](#invalid_idempotency_key).
- PostHog keeps a key for 24 hours.

What PostHog does with a key that it saw before:

| The second request | Result |
| --- | --- |
| is the same as the first, and the first was queued | The first `202`, with the same message ID. Nothing new is sent, and PostHog runs no checks again. Python's result has `replayed` set. |
| is the same as the first, and the first is still in progress | `409` with the name `concurrent_idempotent_requests`. See [`idempotency_key_in_flight`](#idempotency_key_in_flight). The SDKs retry it. |
| differs from the first, or goes to the other send route | `422` [`idempotency_key_reused`](#idempotency_key_reused), with the name `invalid_idempotent_request`. Nothing is sent. |

A request counts as the same when it names the same template (`template_id` or `template_key`), recipient, distinct ID, `template_data`, and content, with the same sender, copies, headers, tags, and attachments. A send that names no `from` stays the same when the project's default sender changes.

Template sends and code sends share one set of keys, so a key names one email across both send routes.

A replay answers before the checks run, so a retry still gets its `202` when the email's workflow was paused after the first send, or when the default sender changed. A retry can still fail when the template is deleted (`404`), when a local template's content changed (`409` [`template_outdated`](#template_outdated)), or when the project no longer has a default sender (`400` [`sender_not_verified`](#sender_not_verified)).

### What the SDKs retry

The SDKs retry a send that failed with a network error, the in-flight `409`, `429` [`throttled`](#throttled), or `503`, each time with the same idempotency key. They wait 1 second, then 2 seconds, with some jitter, or the time in the `Retry-After` header when that is longer, up to 30 seconds.

They never retry [`quota_limited`](#quota_limited): waiting doesn't fix a monthly quota. They retry no other error, because the same request gets the same answer.

### When a job runner retries

When a job runner, such as a queue worker, already retries the job that sends, turn the SDK's retries off and derive the key from the email's purpose:

<MultiLanguage>

```js
const { error } = await posthog.emails.send({
    to: user.email,
    distinctId: user.id,
    templateKey: 'welcome',
    subject: 'Welcome to Hedgebox, {{ variables.first_name }}',
    html: welcomeHtml,
    templateData: { first_name: user.firstName },
    idempotencyKey: `welcome:${user.id}`,
    maxRetries: 0,
})

if (error) {
    // Fail the job, so the job runner retries it with the same key
    throw new Error(`${error.code}: ${error.message}`)
}
```

```python
posthog.emails.send(
    to=user.email,
    distinct_id=user.id,
    template_key='welcome',
    subject='Welcome to Hedgebox, {{ variables.first_name }}',
    html=welcome_html,
    template_data={'first_name': user.first_name},
    idempotency_key=f'welcome:{user.id}',
    max_retries=0,
)
```

</MultiLanguage>

A UUID that the SDK makes is new for each run of the job, so a job retry would send a second email. A key like `welcome:user_123` stays the same in every run.

Node.js returns the error instead of throwing it, so throw it yourself to fail the job. In Python, `send` raises an `EmailError`. Retry only what the SDKs would retry, listed in [what the SDKs retry](#what-the-sdks-retry). Any other error gets the same answer on every run, so stop the job and fix the call.

### What a key promises

A key promises one send per key when you retry. It doesn't promise that an email is delivered exactly once. In rare cases, a failure inside PostHog between accepting a send and queuing it can queue the email twice.

## Engagement capture

PostHog captures the engagement events of an email (sent, delivered, opened, clicked, bounced) as analytics events of the recipient. They count as analytics events in your project.

- For an email from your code, capture is on by default.
- For a template made in PostHog, the project's setting applies.
- To turn it off for one send, pass `captureEngagement: false` (`capture_engagement=False` in Python).

## Results and errors in the SDKs

Both SDKs report the same fields for an error:

| Node.js | Python | Description |
| --- | --- | --- |
| `name` | `name` | The error's name, from [Resend's error names](https://resend.com/docs/api-reference/errors), such as `rate_limit_exceeded`. Code that you move from Resend and that branches on `name` keeps working. |
| `code` | `code` | PostHog's stable code to branch on. Each code has a section in [errors](#errors). |
| `message` | `message` | What happened. |
| `why` | `why` | Why PostHog refused the send, when PostHog says. |
| `fix` | `fix` | What to change before you retry, when PostHog says. |

| `field` | `field` | The request field that the error is about, when there is one. |

| `409` | [`idempotency_key_in_flight`](#idempotency_key_in_flight) | `concurrent_idempotent_requests` | Yes |

## Read an email's status

A `202` means PostHog queued the email. To see where it is later, read its status by the ID that the send returned. The key needs the `hog_flow:read` scope, and `hog_flow:write` covers it.

<MultiLanguage>

```js
const { data, error } = await posthog.emails.get(sent.id)

if (data?.status === 'bounced') {
    console.log(`Bounced: ${data.reason}`)
}
```

```bash
curl "<ph_app_host>/api/projects/@current/messaging/emails/01a146ff-a14e-0000-81c0-f2ccc2444f5f/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY"
```

</MultiLanguage>

The response is `200`:

```json
{
  "id": "01a146ff-a14e-0000-81c0-f2ccc2444f5f",
  "status": "delivered",
  "created_at": "2026-10-23T09:12:04Z",
  "status_at": "2026-10-23T09:12:07Z"
}
```

- `status` moves forward in this order, and never back: `queued`, `waiting`, `unknown`, `skipped`, `failed`, `sent`, `delivered`, `bounced`, `complained`. A late `sent` never replaces `delivered`. It isn't Resend's `last_event`.
- `reason` is there for `skipped`, `failed`, `bounced`, and `complained`, such as `recipient_suppressed`, `provider_error`, or `hard`.
- `created_at` is when PostHog accepted the send, and `status_at` is when the email reached its status. In Node.js, they are `createdAt` and `statusAt`.

PostHog keeps a status for 30 days. A new email can take a few seconds to show up, and until then the read answers `404` [`not_found`](#not_found). The read never retries, so read again later for a newer status. It shares the [rate limits](#rate-limits) of the send. posthog-python has no read yet, so call the route from Python.

### Find the emails sent to an address

`GET /api/projects/@current/messaging/emails/?to=jane@example.com`

The same read, by recipient: the statuses of the recent emails sent to one address, newest first, in pages. Each item has the fields of the read by ID. The key needs `hog_flow:read`, and the read shares the send's rate limits.

```bash
curl -G "<ph_app_host>/api/projects/@current/messaging/emails/" \
  --data-urlencode "to=jane@example.com" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY"
```

## Send over HTTP

The SDKs call these routes. To send from another language, call them yourself.

### Send an email

`POST /api/projects/:project_id/messaging/send/email/`

With a project secret API key, use `@current` as the project ID. A template made in PostHog goes by its ID in `template`:

```bash
curl -X POST "<ph_app_host>/api/projects/@current/messaging/send/email/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: welcome:user_42" \
  -d '{
    "template": { "id": "01a14631-40b7-0000-4dfd-60cd5a2e12ad" },
    "to": "jane@example.com",
    "identifiers": { "distinct_id": "user_42" },
    "message_data": { "first_name": "Jane", "login_url": "https://hedgebox.example.com/login" }
  }'
```

Rendered content goes by `template_key`, with the content in the body:

```bash
curl -X POST "<ph_app_host>/api/projects/@current/messaging/send/email/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: password-reset:user_42:7f3c" \
  -d '{
    "template_key": "password-reset",
    "to": "jane@example.com",
    "identifiers": { "distinct_id": "user_42" },
    "subject": "Reset your password",
    "html": "<p>Hi Jane,</p><p><a href=\"https://hedgebox.example.com/reset?token=7f3c\">Reset your password</a>.</p>",
    "from": "Hedgebox <security@example.com>"
  }'
```

A local template goes by its key and its [content hash](#content-hash) in `template`, with `message_data`. When PostHog answers [`template_outdated`](#template_outdated), [upload the template](#upload-a-template-by-key), then send again with the same `Idempotency-Key`. The hash must describe the content that you upload: the upload response returns it as `content_hash`. This example sends the template of the [upload example](#upload-a-template-by-key):

```bash
curl -X POST "<ph_app_host>/api/projects/@current/messaging/send/email/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: welcome:user_42" \
  -d '{
    "template": { "key": "welcome", "hash": "v1:67bd514eca757ac54081c4eda9ca9cc9d3704594f0d83843a76a77364a2c6a12" },
    "to": "jane@example.com",
    "identifiers": { "distinct_id": "user_42" },
    "message_data": { "first_name": "Jane" }
  }'
```

| SDK parameter | Request | Description |
| --- | --- | --- |
| `to` | `to` | Required. The recipient's email address. |
| `distinct_id` | `identifiers.distinct_id` | The distinct ID of the recipient's person. Defaults to the recipient's email address. [Always pass it](#always-pass-distinct_id). |
| `template_id` | `template.id` | A template made in PostHog. |
| `template_key` with `template_data` | `template.key` and `template.hash` | A local template, by its key and the [content hash](#content-hash) of the content you hold. `hash` only goes with `key`. |
| `template_data` | `message_data` | Values for the template's `{{ variables.* }}` placeholders. Not with rendered content. |
| `template_key` without `template_data` | `template_key` | Rendered content, named by its key. Send it with `subject`, and `html`, `text`, or both. |
| `subject`, `html`, `text` | `subject`, `html`, `text` | The rendered content. Without `text`, PostHog derives it from `html`. |
| `from` | `from` | The sender, on a domain that the project verified. Not with `template.id`. |
| `reply_to` | `reply_to` | A list of up to 10 addresses. Not with `template.id`. |
| `cc`, `bcc` | `cc`, `bcc` | Lists of up to 10 bare addresses each. Not with `template.id`. |
| `headers` | `headers` | An object of up to 10 header names and values. Not with `template.id`. |
| `tags` | `tags` | A list of up to 10 `{ "name", "value" }` objects. Not with `template.id`. |
| `attachments` | `attachments` | A list of up to 10 `{ "filename", "content", "content_type", "content_id" }` objects, with `content` in Base64. At most 512 KB in total after decoding. Not with `template.id`. |
| `capture_engagement` | `capture_engagement` | Whether PostHog captures the email's [engagement events](#engagement-capture). Leave it out for the default. |
| `idempotency_key` | `Idempotency-Key` header | The send's [idempotency key](#idempotency). Send one on every request. |

A request names exactly one of `template` and `template_key`. The rules for each field are in [add copies, headers, tags, and attachments](#add-copies-headers-tags-and-attachments).

PostHog refuses a field that the route doesn't take with `400` [`invalid_request`](#invalid_request), and `attr` names the field. A newer SDK against an older PostHog then fails, instead of sending the email without part of the request.

The response is `202`:

```json
{ "message_id": "01a146ff-a14e-0000-81c0-f2ccc2444f5f", "replayed": false, "warnings": [] }
```

`message_id` identifies the queued send. `replayed` is `true` when an earlier request with the same `Idempotency-Key` already queued this email. `warnings` is empty, or holds a [`template_superseded`](#template_superseded) warning as `{ code, detail, fix }`.

### Send with a content hash

Add `hash` next to `key` to check that PostHog holds the content that you hold:

| The hash is | Result |
| --- | --- |
| absent | PostHog sends the published content. |
| the current hash | PostHog sends the published content. |
| a hash that newer content replaced | PostHog sends the current content, with a [`template_superseded`](#template_superseded) warning. |
| a hash PostHog never published, or a key PostHog doesn't know | `409` [`template_outdated`](#template_outdated). PostHog queues nothing. Upload the template, then send again. |

### Content hash

The content hash is the SHA-256 of the template's subject, preheader, HTML, and text, written as `v1:` and 64 lowercase hex characters. The SDKs compute it for a local template, which has no preheader. To compute it in another language:

1. Use the empty string for a field that is absent.
2. Replace `\r\n` and lone `\r` with `\n`. Change nothing else: no trimming, no Unicode normalization.
3. Start with the UTF-8 bytes of `posthog-email-template-v1\n`.
4. For each field, in the order subject, preheader, HTML, text, add its UTF-8 byte length in decimal, then `:`, then its UTF-8 bytes, then `\n`.
5. Hash the bytes with SHA-256.

Test it against this case: the subject `Welcome, {{ variables.first_name }}`, the HTML `<p>Hi {{ variables.first_name }}</p>`, no preheader, and no text hash to `v1:f74cd913f3aa2e5667a588f2865634e56693df77793ca594d18e9b5f89e3d2e6`.

The upload response carries the hash too, as `content_hash`.

### Send by template ID in the path

`POST /api/projects/:project_id/messaging_templates/:id/send/`

This older route names the template by its ID in the path. Its body is `to`, `identifiers`, and `message_data`, and it answers `202 { "message_id": ..., "replayed": false }`. It takes an `Idempotency-Key` too. The template must be transactional first. It takes no content hash and returns no warnings. Use the [send route](#send-an-email) for new code.

### Rate limits

The upload route and both send routes share one rate limit per API key, and one across all project secret API keys of a project. When you go over it, PostHog answers `429` with the code [`throttled`](#throttled), and the SDKs retry. A project over its email quota gets `429` with the code [`quota_limited`](#quota_limited) instead, and the SDKs don't retry.

## Upload a template by key

`PUT /api/projects/:project_id/messaging_templates/by_key/:key/`

The SDKs call this route for a [local template](#send-a-local-template) when PostHog doesn't hold its content. Call it yourself to send a local template from another language, to upload in a deploy step, or to roll back. With a project secret API key, use `@current` as the project ID. A personal API key or a session can call it too, with editor access to Workflows.

```bash
curl -X PUT "<ph_app_host>/api/projects/@current/messaging_templates/by_key/welcome/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Welcome",
    "subject": "Welcome to Hedgebox, {{ variables.first_name }}",
    "html": "<p>Hi {{ variables.first_name }}</p>",
    "source": { "repository": "github.com/example/app", "path": "emails/welcome.html", "ref": "3f2c1ab" }
  }'
```

| Field | Type | Description |
| --- | --- | --- |
| `name` | string, required | Name in the template library. At most 400 characters. |
| `subject` | string, required | Subject line. Supports Liquid. |
| `html` | string, required | HTML body, stored as you send it. Supports Liquid. |
| `text` | string | Plain-text body. Leave it out to remove the stored one. |
| `preheader` | string | Inbox preview text. Leave it out to remove the stored one. |
| `source` | object | `{ repository, path, ref }`, each a string of at most 400 characters. Shown in PostHog next to the template. Leave it out, or leave out a part, to keep what is stored. |
| `if_not_superseded` | boolean | Refuse to publish content that newer content already replaced. See [automatic uploads](#automatic-uploads-and-if_not_superseded). |
| `if_code_managed` | boolean | Refuse to overwrite a template whose content people edit in PostHog. The upload answers `409` [`template_edited_in_posthog`](#template_edited_in_posthog) and writes nothing. Without it, the upload claims such a template, as in [adoption](#adopt-a-template-made-in-posthog). |

PostHog stores `subject`, `preheader`, `html`, and `text` byte for byte. It doesn't trim whitespace, so the hash you compute matches the hash PostHog stores.

The response:

```json
{
  "id": "01a14631-40b7-0000-4dfd-60cd5a2e12ad",
  "key": "welcome",
  "result": "created",
  "content_hash": "v1:67bd514eca757ac54081c4eda9ca9cc9d3704594f0d83843a76a77364a2c6a12",
  "managed_by": "code",
  "source": { "repository": "github.com/example/app", "path": "emails/welcome.html", "ref": "3f2c1ab" },
  "transactional_hog_flow_id": "01a14631-40c1-0000-d930-cf5400ef453a"
}
```

| `result` | Status | What happened |
| --- | --- | --- |
| `created` | `201` | No template had this key. PostHog created one, marked it as managed by code, and made it transactional with the project's default sender. |
| `updated` | `200` | PostHog published the uploaded content. The next send uses it. |
| `unchanged` | `200` | The template already had this name and content. PostHog wrote nothing, except source parts that changed. |
| `superseded` | `200` | Only with `if_not_superseded`. Newer content replaced this content, so PostHog wrote nothing. `content_hash` is the current hash. |

An upload never turns a paused template back on. It keeps the template's sender, unless the template's workflow was deleted: then the upload creates a new workflow with the project's default sender. When two first uploads of one key run at the same time, both succeed and one template exists.

### Automatic uploads and `if_not_superseded`

An automatic upload, like the one the SDKs make after `template_outdated`, should set `"if_not_superseded": true` and `"if_code_managed": true`. Between the `409` and the upload, another instance can publish the same content and a newer deploy can replace it. With the option, the upload answers `superseded` and writes nothing, so the old content doesn't come back. Send again, and the email goes out with the current content and a [`template_superseded`](#template_superseded) warning.

Leave `if_not_superseded` out for an upload that you make on purpose, such as a rollback.

## Templates managed by code

A template that an upload created, or that an upload claimed, is managed by code. In the Workflows template library:

- It shows a **Managed by code** tag.
- It shows its key, and the file it came from: the path, the repository, and the commit or branch of the last upload. Each part links to the file when PostHog knows the host.
- It opens as a read-only **Preview** of the subject, preheader, HTML, and text. You can't edit, save, or delete it there, because the next upload would overwrite your changes. To change it, change its file. See [change a code-managed template](#change-a-code-managed-template).
- **Duplicate** makes an editable copy, with no key.

The same rule applies over the API and the [PostHog MCP](/docs/workflows/surfaces/mcp): an update, a design edit, or a delete answers `403` [`immutable`](#immutable). Uploads and sends still work.

To edit the template in PostHog instead, stop managing it in code. On the template page, open the menu and click **Stop managing in code**. Over the API, send a `PATCH` whose only field is `managed_by`, with a personal API key:

```bash
curl -X PATCH "<ph_app_host>/api/projects/:project_id/messaging_templates/:id/" \
  -H "Authorization: Bearer $POSTHOG_PERSONAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "managed_by": "gui" }'
```

The template keeps its key. The next upload under that key without `if_code_managed` manages it in code again. The SDKs' automatic upload sets `if_code_managed`, so it doesn't take the template back. A send whose content PostHog still holds keeps working. A send that needs an upload, because your content changed, fails with [`template_edited_in_posthog`](#template_edited_in_posthog).

The lock covers the template only. Its linked workflow stays editable.

## Change a code-managed template

A code-managed template changes in its file, in your repository. PostHog doesn't edit the file. The template page gives you a prompt for your coding agent, and can ask PostHog Code to open a pull request.

### Edit with your agent

1. Open the template in the Workflows template library, and click **Edit with your agent**.
2. Under **Describe the change**, complete the sentence. It starts with the file, for example ``In `emails/welcome.html`, change``. When PostHog doesn't know the file's path, it starts with ``In the HTML file of the `welcome` email template, change``.
3. Click **Copy prompt**. It stays disabled with "Describe the change first" until you add to the sentence. To read the whole prompt first, open **Show full prompt**.
4. Paste the prompt into your coding agent, in a checkout of the template's repository. The agent changes the file.

The prompt is your sentence, then a block that PostHog builds from the template. It leaves out each detail that it doesn't know:

```text
In `emails/welcome.html`, change the button color to green.

About this file:
- It is the PostHog email template with the key `welcome`, in the repository `github.com/example/app`, last uploaded from commit `3f2c1ab`.
- The file is the whole email. The subject is the first `<title>`. The inbox preview text is the `content` of `<meta name="preheader">`. Everything in the file is the HTML that PostHog sends.
- Personalize only with `{{ variables.<name> }}`. The values come from the `data` the app passes to `posthog.emails.send`. This file uses `{{ variables.first_name }}` and `{{ variables.login_url }}`.
- Do not upload the file by hand. If the app sends it with `posthog.emails.templateFile()`, the next send uploads the changed file. If the app sends it by the key `welcome`, upload the file again after the change (PUT /api/projects/@current/messaging_templates/by_key/welcome/ or the PostHog MCP upload tool).
- The template in PostHog: <ph_app_host>/project/:project_id/workflows/library/templates/:id
```

The path, repository, and commit come from the template's [source details](#where-the-source-details-come-from). Without a path, the first point of the block tells the agent to find the file in the app by the template's key.

An agent that reads the template over the API or the [PostHog MCP](/docs/workflows/surfaces/mcp) gets the same text: the template's `change_prompt_starter` is the start of the sentence, `change_prompt_context` is the block, and `change_prompt_variables` lists the variables the block names. All three are `null` for a template that isn't managed by code.

### Run with PostHog Code

When your organization can use PostHog Code, the popover also shows **Run with PostHog Code**. It sends your sentence to PostHog Code, which starts a task on the template's GitHub repository. The task changes only the template's file and opens a pull request. It never uploads the template. A toast and the notice on the page link to the task.

The button is disabled when:

- "You don't have sufficient permissions for this workflow.", followed by your access level and the required one: starting a task needs editor access to Workflows. Ask a project admin for it.
- "PostHog doesn't know this template's GitHub repository": the template's source has no repository. Upload the template with its [repository](#where-the-source-details-come-from), such as `github.com/example/app`. A repository that isn't on GitHub answers [`template_repository_unsupported`](#template_repository_unsupported) when you click.
- "Checking the GitHub connection": PostHog is still loading the project's integrations.
- "Connect GitHub to run PostHog Code": the project has no GitHub integration. Connect GitHub in the project's integrations, and give the PostHog app access to the repository.
- "Shorten the change to 2,000 characters": the sentence is longer than the route takes.
- "Describe the change first": the sentence has nothing after the start.

When PostHog Code can't start, the popover shows the error and its fix, and keeps your sentence. If you closed the popover first, a toast shows them. Each click that succeeds starts another task.

You can start the same task over the API, with a personal API key or OAuth that has the `hog_flow:read` and `task:write` scopes and editor access to Workflows. `hog_flow:write` covers `hog_flow:read`. A project secret API key can't start a task.

```bash
curl -X POST "<ph_app_host>/api/projects/:project_id/messaging_templates/:id/request_change/" \
  -H "Authorization: Bearer $POSTHOG_PERSONAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "instruction": "Make the button green." }'
```

- `instruction` is required, with at most 2,000 characters, such as `Make the button green.` When it doesn't start with the template's `change_prompt_starter`, PostHog puts the starter and `what this request asks for:` in front of it, so the task knows the file.
- The response is `201` with `task_id`, `task_url`, and `repository` (`owner/name`).
- The PostHog MCP tool `workflows-request-email-template-change` calls this route.
- The errors are [`instruction_missing`](#instruction_missing), [`template_not_managed_by_code`](#template_not_managed_by_code), [`template_repository_missing`](#template_repository_missing), [`template_repository_unsupported`](#template_repository_unsupported), [`github_repository_not_connected`](#github_repository_not_connected), [`posthog_code_not_available`](#posthog_code_not_available), and [`posthog_code_run_failed`](#posthog_code_run_failed).

Use it only when you can't change the file yourself. A coding agent whose workspace holds the repository, or that runs outside PostHog Code and can check it out, edits the file that `change_prompt_context` names, as it describes. Inside PostHog Code, such as PostHog AI or the Slack bot, the route refuses the call with [`posthog_code_not_available`](#posthog_code_not_available).

### Ask PostHog AI or the Slack bot

[PostHog AI](/docs/posthog-ai) and the [PostHog bot in Slack](/docs/posthog-ai/surfaces/slack) run inside PostHog Code, and a running PostHog Code task can't start another one. So when you ask either of them to change a code-managed template, it can't open a pull request. It gives you the link to the template instead. Open it, click **Edit with your agent**, describe the change, and click **Run with PostHog Code** to open the pull request.

A coding agent that has a checkout of the repository, such as one connected to the PostHog MCP in your editor, changes the file itself.

### Copy the HTML file

A template that was uploaded without a file, for example by an agent over the MCP, has no file in your repository yet. To make one, click the arrow next to **Edit with your agent**, then **Copy HTML file**. Save the result in your repository, such as `emails/welcome.html` for the key `welcome`, and send it as a [local template](#send-a-local-template) with the template's key as `template_key`. With another key, the first send uploads a new template.

- The subject goes into the first `<title>`, and the preheader into `<meta name="preheader">`. Pass the subject to the send as `subject`.
- A template that came from a file copies back as that file, byte for byte.
- The file has no plain-text part. When the template has one, the toast adds: "This file has no plain-text part. The next upload from this file removes the plain-text version."

### When the change goes live

Copying a prompt or a file, or starting a PostHog Code task, changes nothing in PostHog. PostHog keeps sending the current version of the template until your app sends the changed template as a [local template](#send-a-local-template), or you upload it. For a pull request, that is after you merge it and deploy your app. When something other than an SDK sends the template, such as a cURL call, upload the file after the merge.

## Where the source details come from

An upload's `source` tells PostHog where the template's file is: the `repository`, the `path` of the file in it, and the `ref` it was uploaded from. PostHog shows them on the template and puts them in the [agent prompt](#edit-with-your-agent). [Run with PostHog Code](#run-with-posthog-code) needs the repository.

The SDKs' automatic upload of a [local template](#send-a-local-template) sends no `source`. PostHog keeps the source details that an earlier upload stored.

To set them, upload the template over HTTP or the MCP with `source`: the repository from `git remote get-url origin`, as `host/owner/name` without credentials, the path relative to the repository's root, and the ref from `git rev-parse HEAD`.

## Adopt a template made in PostHog

You can move a template that you made in PostHog into code without changing its ID, workflow, sender, or history. Give it a key with a `PATCH` whose only field is `key`:

```bash
curl -X PATCH "<ph_app_host>/api/projects/:project_id/messaging_templates/:id/" \
  -H "Authorization: Bearer $POSTHOG_PERSONAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "key": "welcome" }'
```

- Use a personal API key or the app, with editor access to the template's workflow. A project secret API key can't set a key.
- A key is set once. A template that has a key keeps it.
- PostHog never matches a template by its name. An upload under an unknown key always creates a new template.

To claim the template, [upload](#upload-a-template-by-key) your content under that key once, without `if_code_managed`. The upload publishes your content and marks the template as managed by code. After that, the SDKs send it as a [local template](#send-a-local-template). Before that, a local template send under that key works only when PostHog holds its content. The current content goes out as it is. Content from one of the last 100 publishes goes out as the current content, with a [`template_superseded`](#template_superseded) warning. Content that PostHog never published needs an upload, so the send fails with [`template_edited_in_posthog`](#template_edited_in_posthog): the SDKs' automatic upload never claims a template that people edit in PostHog.

When you delete a template, its key is free again. The next upload under that key creates a new template.

## Errors

Every error has a JSON body with a stable `code`:

```json
{
  "type": "invalid_request",
  "code": "template_outdated",
  "detail": "No template in this project has the key `welcome`, so nothing was sent.",
  "attr": "template__key",
  "why": "PostHog holds no content for this key yet.",
  "fix": "Upload the template with `PUT /api/projects/@current/messaging_templates/by_key/welcome/`, then send again. posthog-node does this on its own.",
  "docs_url": "https://posthog.com/docs/workflows/transactional-email-api#template_outdated"
}
```

- `code` is the value to branch on. It stays the same while the wording of the other fields can change.
- `detail` says what happened, `why` says why, and `fix` says what to change.
- `attr` names the request field the error is about, such as `subject` or `template__key` (`template.key`), or is `null`.
- `docs_url` links to the section for the code below.
- Some codes don't carry `why`, `fix`, and `docs_url` yet, such as the codes shared with the rest of the PostHog API (`not_found`, `authentication_failed`, `not_authenticated`, `permission_denied`, `throttled`). Look up their `code` on this page. Each section gives the fix.

The SDKs add `name`, and turn `detail` into `message`, `attr` into `field`, and `docs_url` into `docsUrl` (`docs_url` in Python). See [results and errors in the SDKs](#results-and-errors-in-the-sdks).

### `invalid_template_key`

`400` on the upload, the send, and adoption.

The key has a character other than a letter, a digit, a hyphen (`-`), or an underscore (`_`), or has more than 400 characters. The API says: "The key can have at most 400 letters, digits, hyphens (-) and underscores (_)."

**Fix:** Use a key like `password-reset`. Code names the template by its key in every project, so the key must stay the same.

### `invalid_request`

`400` on the upload, the send, adoption, and a change request.

A field is missing, has the wrong type, or breaks a rule. `attr` names the field, and `detail` starts with it, for example `subject: This field is required.` On the send, the API says why: "A send needs a template, a recipient address, and data as an object." A send names exactly one of `template` and `template_key`, `hash` only goes with `key`, and rendered content needs a `subject` and `html` or `text`, and takes no `message_data`. `from`, `reply_to`, `cc`, `bcc`, `headers`, `tags`, and `attachments` don't go with `template.id`. On adoption, `key` must be the only field of the `PATCH`. On a change request, `instruction` has at most 2,000 characters.

**A field the route doesn't take.** The send refuses a field that it doesn't know, such as a field from a newer SDK, and names it in `attr`. The API says: "PostHog doesn't take this field on this route." It says why, for example: "PostHog refuses a field it doesn't know, such as `cc` from a newer SDK, so it never sends the email without part of what you asked for." Update PostHog, or leave the field out.

**Copies, headers, tags, and attachments.** `attr` names the entry, such as `cc__0`, `headers`, `tags__0__name`, or `attachments__0__filename`. The API says, for example:

- "`"jane"@example.com` is not a bare address. Send it as `jane@example.com`." for a `cc` or `bcc` entry in quotes. An entry with a display name, such as `Jane <jane@example.com>`, answers "Enter a valid email address."
- "PostHog sets `Reply-To` itself. Use the send's own fields, such as `from`, `cc` or `subject`, instead."
- "Use only ASCII letters, numbers, `_` and `-`." for a tag.
- "Mailbox providers block `.exe` files. Send a link to the file instead."
- "Attachments can hold 512KB in total. Send a link to larger files."

See [add copies, headers, tags, and attachments](#add-copies-headers-tags-and-attachments) for every rule.

**Fix:** Fix the field that `attr` names, then send the request again. The API says: "Fix `subject` and upload again.", "Fix `template` and send again.", or "Fix `instruction` and request the change again."

### `template_not_sendable`

`400` on the upload and the send.

The template has no subject or no body, so it can't be sent. The API says, for example: "The template has no email subject, so it can't be sent."

**Fix:** Send a subject and HTML. In a template file, put the subject in `<title>`.

### `sender_unavailable`

`400` on an upload that has to make the template transactional: the first upload of a key, or an upload that claims an adopted template or a template whose workflow was deleted.

The project has no verified default sender, so PostHog can't make the template transactional. The upload writes nothing. The API says: "The project has no verified default email sender. Verify a sending domain, set it as the default sender, and upload again."

**Fix:** [Verify a sending domain](/docs/workflows/configure-channels), click **Make default** next to the sender, and upload again.

### `marketing_template`

`400` on the upload and the send.

The template is in a marketing message category. Transactional emails skip opt-outs, so a marketing template can't be sent this way. The API says: "The template is in a marketing category. Only transactional templates can be sent."

**Fix:** Move the template to a transactional category, or remove its category. If the template is managed by code, [stop managing it in code](#templates-managed-by-code) first, or change the category's type.

### `key_already_set`

`400` on adoption.

The template already has a key, and a key never changes. The API says, for example: "This template already has the key `welcome`."

**Fix:** The API says: "Use `welcome` in your code, or duplicate the template and give the copy a key."

### `key_in_use`

`400` on adoption.

Another template in this project has this key. A key names one template in a project. The API says, for example: "Another template in this project has the key `welcome`."

**Fix:** The API says: "Pick another key, or upload your file to the template that has this key."

### `immutable`

`403` on an update, a design edit, or a delete of a template that is managed by code.

The template's content comes from a file in a repository, and the next upload of that file replaces changes made in PostHog. The API says: "This template is managed by code, so it can't be changed in PostHog."

**Fix:** The API names the file when it knows it, for example: "When the repository is in your workspace, or you run outside PostHog Code and can check it out, edit `emails/welcome.html` in `github.com/example/app` there, as the template's `change_prompt_context` describes. It also says how the change goes live. Inside PostHog Code, such as PostHog AI or the Slack bot, share the template's link instead: on its page, the person clicks Edit with your agent, then Run with PostHog Code. Otherwise, ask PostHog Code to open a pull request with the change: call the `workflows-request-email-template-change` tool, or POST an `instruction` to this template's `request_change/` route. To edit the template in PostHog instead, stop managing it in code first: send a PATCH whose only field is `managed_by` set to `gui`." See [change a code-managed template](#change-a-code-managed-template).

### `template_not_found`

`404` on a send by `template_id`.

No template in this project has this ID, or the template is deleted. The API says, for example: "No template in this project has the id `01a14631-40b7-0000-4dfd-60cd5a2e12ad`." It says why: "A send names a template of this project that is not deleted."

**Fix:** The API says: "Check the id and the project." A key that PostHog doesn't know answers [`template_outdated`](#template_outdated) instead.

### `template_outdated`

`409` on a send of a [local template](#send-a-local-template). Nothing was sent.

PostHog doesn't hold the template's content, so it queued nothing:

- **A key PostHog doesn't know yet**, such as the first send of a new local template. The API says: "No template in this project has the key `welcome`, so nothing was sent." It says why: "PostHog holds no content for this key yet."
- **A hash PostHog never published**, because you changed the template. The API says: "PostHog does not hold the content this hash describes, so nothing was sent." It says why: "The template never had this content, so sending its current content could send the wrong email."

**Fix:** The SDKs handle this on their own: they upload the template, then send once more with the same idempotency key. Over HTTP, the API says: "Upload the template with `PUT /api/projects/@current/messaging_templates/by_key/welcome/`, then send again. posthog-node does this on its own.", or for a hash: "Upload the template, then send again. posthog-node does this on its own." For an automatic upload, set [`if_not_superseded` and `if_code_managed`](#automatic-uploads-and-if_not_superseded).

### `not_found`

`404` on the upload route, the send routes, the status read, and the change request route.

The transactional email API isn't enabled for this project, or the template ID in the path doesn't exist. Adoption and release don't check the beta flag, so a successful adoption doesn't mean the API is enabled. The API says: "Not found."

**Fix:** The API is in beta. [Ask us in-app](https://app.posthog.com/#panel=support%3Afeedback%3A%3Alow%3Atrue) to enable it for your project. Don't retry until it's enabled. If it's already enabled, check the project and the template ID.

On a [status read](#read-an-emails-status), no email in this project has the ID, the email is older than 30 days, or it was sent a few seconds ago. The API says, for example: "No email in this project has the id `01a146ff-a14e-0000-81c0-f2ccc2444f5f`." It says why: "PostHog keeps an email's status for 30 days. A new email can take a few seconds to show up." **Fix:** The API says: "Check the `message_id` the send answered and the project, or read again in a few seconds."

### `authentication_failed`

`401` on every route.

PostHog doesn't accept the key. For example, the key is wrong, deleted, or rolled. A missing `Authorization` header answers `401` with the code `not_authenticated`.

**Fix:** Send a project secret API key (`phs_`) as `Authorization: Bearer <key>`. In the SDKs, set the `secretKey` option (`secret_key` in Python).

### `permission_denied`

`403` on every route.

The key can't do this. For example:

- "API key missing required scope 'hog_flow:write'": give the key the `hog_flow:write` scope. A [change request](#run-with-posthog-code) needs `hog_flow:read` and `task:write` instead, and names the first one the key lacks, such as "API key missing required scope 'task:write'".
- "This action does not support project secret API key access": a project secret API key can only upload, send, and read an email's status. Use a personal API key for other template routes, such as [adoption](#adopt-a-template-made-in-posthog) and a [change request](#run-with-posthog-code).
- "You need editor access to this template's transactional email workflow.": a personal API key or a session needs editor access to the template's workflow.
- "You need editor access to workflows to upload a new template.": a personal API key or a session needs editor access to Workflows to create a template.
- "You need editor access to workflows to make a template transactional.": a personal API key or a session needs editor access to Workflows to make a template transactional.
- "You do not have editor access to this resource.": a personal API key or a session needs editor access to Workflows for this route, such as a [change request](#run-with-posthog-code).
- "API key does not have access to the requested project: ID ...": the key can't access the project in the URL. With a project secret API key, use `@current`. With a personal API key, use the ID of a project that the key can access.

**Fix:** For the upload and send routes, use a project secret API key with `hog_flow:write` for the project that has the template. For other routes, use a personal API key with `hog_flow:write`, or with `hog_flow:read` and `task:write` for a [change request](#run-with-posthog-code), and the access that the route's section names.

### `throttled`

`429` on every route.

Too many calls in a short time. The upload route and both send routes share one limit per API key, and one across all project secret API keys of a project. The API says, for example: "Request was throttled. Expected available in 30 seconds."

**Fix:** Wait for the number of seconds in the `Retry-After` header, then send again with the same idempotency key. The SDKs do this on their own.

### `template_not_transactional`

`400` on the send.

The template has no workflow to send it, for example a template made in PostHog that you gave a key but never uploaded. The API says: "The template isn't transactional. Make it transactional to send it."

**Fix:** Upload the template by its key, or make it transactional in PostHog.

### `transactional_email_paused`

`400` on the send.

The email's workflow is paused or deleted. PostHog checks this after it looks up the idempotency key, so a retry of a send that PostHog already queued still gets its `202`. See [idempotency](#idempotency).

- "The email's workflow isn't an active transactional email.": the workflow is paused. The API says why: "PostHog sends a transactional email only while its workflow is active." **Fix:** The API says: "Turn the email's workflow back on, then send again." An upload never turns a paused workflow back on.
- "The template's transactional email no longer exists.": the workflow was deleted. **Fix:** Upload the template again. The upload creates a new workflow with the project's default sender. For a template without a key, call `POST /api/projects/:project_id/messaging_templates/:id/make_transactional/` with a personal API key that has `hog_flow:write` and editor access to Workflows.

### `invalid_recipient`

`400` on the send.

PostHog can't use the recipient address. The API says: "The recipient address can't contain { or }." An address that isn't a valid email address answers [`invalid_request`](#invalid_request) with `attr` set to `to`.

**Fix:** Send one valid email address in `to`. When you send to many people, skip the recipient that failed and keep sending to the others.

### `quota_limited`

`429` on the send.

The project is over its email quota. The API says: "The project is over its email quota."

**Fix:** Check your [sending allowance](/docs/workflows/sending-reputation), or wait for the next period. The SDKs don't retry this, because waiting a few seconds doesn't change a monthly quota.

### `delivery_unavailable`

`503` on the send.

PostHog's email pipeline or its idempotency store is down, so PostHog queued nothing. The API says: "The email pipeline is unavailable. Try again shortly."

**Fix:** Send again with the same idempotency key. The SDKs retry this on their own.

### `sender_not_verified`

`400` on a send. Nothing was sent.

PostHog has no sender it can send from. For a send without `from`, the API says: "The project has no verified default email sender." It says why: "The send names no `from`, and the project has no verified default sender to send from."

**Fix:** The API says: "Pass `from` with an address on a verified domain, or set a default sender in the email channel settings." See [set up the email channel](/docs/workflows/configure-channels). A `from` that no verified sender can send from answers [`sender_not_allowed`](#sender_not_allowed) instead.

When the sender of a template made in PostHog stops working, the `why` and the `fix` name the reason:

| `why` | `fix` |
| --- | --- |
| "The sender configured for this email no longer exists." | "Select a new sender for the email." |
| "The sender configured for this email is not an email channel." | "Select an email sender for the email." |
| "The sender's domain is not verified." | "Verify the domain in the email channel settings, then send again." |
| "The sender has no address or no name." | "Set the address and name of the sender in the email channel settings." |

### `sender_not_allowed`

`400` on a send. Nothing was sent.

No verified sender of the project can send from the address in `from`, and `attr` is `from`. The API says, for example: "No verified sender in this project can send from `security@example.com`." It says why: "PostHog only sends from a domain the project verified, so mailbox providers trust the email."

**Fix:** The API says: "Send from an address on a verified domain, or verify the domain in the email channel settings first." Or leave out `from` to send from the project's default sender. See [set up the email channel](/docs/workflows/configure-channels).

### `recipient_suppressed`

`400` on a send. Nothing was sent.

An earlier email to the address bounced, or the recipient marked it as spam, so PostHog no longer sends to it. This covers every recipient: when the `to` address, a `cc`, or a `bcc` address is suppressed, PostHog sends nothing. The API says why, for example: "An earlier email to jane@example.com bounced or was marked as spam, so PostHog no longer sends to it."

**Fix:** The API says: "Send to another address, or remove the address from the suppression list once it can receive email again."

### `sending_suspended`

`400` on a send. Nothing was sent.

Email sending is stopped for the whole project. The `why` and the `fix` name the reason:

| `why` | `fix` |
| --- | --- |
| "Email sending is suspended for this project." | "Contact support to get sending re-enabled." |
| "Our email provider paused sending for this project." | "Check the Reputation tab to see what to fix." |

See [sending reputation](/docs/workflows/sending-reputation).

### `template_paused`

`400` on a send. Nothing was sent.

Email sending is paused for the email's workflow. The `why` and the `fix` name who paused it, and add the reason when there is one:

| `why` | `fix` |
| --- | --- |
| "Email sending is paused for this email's workflow." | "Resume it from the workflow page once the audience is cleaned up." |
| "PostHog staff paused email sending for this email's workflow." | "Contact support to get sending re-enabled." |

### `template_edited_in_posthog`

`409` on a send of a [local template](#send-a-local-template), and on an upload with `if_code_managed`. Nothing was sent.

The template key names a template that people edit in PostHog, so the SDK's upload changed nothing. The API says, for example: "The template `welcome` is edited in PostHog, so the upload changed nothing and nothing was sent." It says why: "An upload from code would overwrite the content people edited in PostHog."

**Fix:** The API says: "Send the email under another `template_key`, or upload without `if_code_managed` to replace the content edited in PostHog with yours." The SDKs don't retry this.

### `idempotency_key_in_flight`

`409` on a send. The SDKs report it with the name `concurrent_idempotent_requests`.

A request with the same idempotency key is still in progress. The API says: "A request with this Idempotency-Key is still being processed. Retry in a few seconds."

**Fix:** Send again with the same key in a few seconds. The SDKs retry this on their own. When the first request queued the email, the retry gets its `202` and sends nothing new.

### `idempotency_key_reused`

`422` on both send routes. Nothing was sent. The SDKs report it with the name `invalid_idempotent_request`.

The idempotency key was used before with another request, or on the other send route. A key names one email, so PostHog doesn't send a different email under it. The API says: "This Idempotency-Key was already used for a different request. Use a new key for a new email."

**Fix:** Use a new key for a new email. When you derive the key from the email's purpose, such as `welcome:user_123`, put everything that makes the email different into the key. See [idempotency](#idempotency).

### `invalid_idempotent_request`

The SDKs' `name` for [`idempotency_key_reused`](#idempotency_key_reused), from Resend's error names. PostHog answers the code `idempotency_key_reused`.

### `invalid_idempotency_key`

`400` on a send. Nothing was sent.

The key in the `Idempotency-Key` header has the wrong form. The API says: "The Idempotency-Key header must be 1 to 255 visible ASCII characters, with no spaces."

**Fix:** Use a key like `welcome:user_123`, or leave it out and let the SDK make one.

### `instruction_missing`

`400` on a [change request](#run-with-posthog-code).

The request has no `instruction`, or it is blank. The API says:

- `detail`: "The request has no instruction."
- `why`: "PostHog Code needs to know what to change in the template's file."
- `fix`: "Send the change in `instruction`, such as `Make the button green.`"

### `template_not_managed_by_code`

`400` on a [change request](#run-with-posthog-code).

The template was made in PostHog, or it is no longer managed by code, so there is no file to change. The API says:

- `detail`: "This template is not managed by code, so it has no file for PostHog Code to change."
- `why`: "Only a template uploaded from a file in a repository has a file to change."
- `fix`: "Edit the template in PostHog instead: in the template editor, or with a PATCH to the template."

### `template_repository_missing`

`400` on a [change request](#run-with-posthog-code).

No upload of the template sent a repository, so PostHog Code doesn't know where to open the pull request. The API says:

- `detail`: "PostHog doesn't know which repository this template's file is in."
- `why`: "The uploads of this template sent no `source.repository`."
- `fix`: "Upload the template again with `source.repository`, such as `github.com/example/app`. posthog-node detects it from the git checkout or the CI environment when the upload doesn't set it."

See [where the source details come from](#where-the-source-details-come-from).

### `template_repository_unsupported`

`400` on a [change request](#run-with-posthog-code).

The template's repository isn't on GitHub, or isn't stored as `github.com/<owner>/<name>`. The API says, for example:

- `detail`: "PostHog Code can't change files in `gitlab.com/example/app`." When the stored repository doesn't look like one: "PostHog Code can't change files in this template's repository."
- `why`: "PostHog Code opens pull requests only on GitHub repositories, stored as `github.com/<owner>/<name>`."
- `fix`: "Edit the template's file in its repository, as its `change_prompt_context` describes."

[Edit with your agent](#edit-with-your-agent) works for any repository.

### `github_repository_not_connected`

`400` on a [change request](#run-with-posthog-code).

The project's GitHub integration can't reach the template's repository. The API says, for example:

- `detail`: "This project's GitHub integration can't reach `example/app`."
- `why`: "PostHog Code works only in repositories that the project's GitHub integration can reach."
- `fix`: "Connect GitHub in the project's integrations and give the PostHog app access to `example/app`, then request the change again. Access you just gave can take a few minutes to show up."

### `posthog_code_not_available`

`403` on a [change request](#run-with-posthog-code).

PostHog Code can't start a task for this request. The API says: "PostHog Code is not available to start this change." The `why` and `fix` name the reason:

| `why` | `fix` |
| --- | --- |
| "A PostHog Code task runs at a person's request, so a task already running can't start another one." | "Share the template's link with the person. On its page, they click Edit with your agent, describe the change, and click Run with PostHog Code, which opens a pull request." |
| "PostHog couldn't check whether this organization can use PostHog Code." | "Try again in a few minutes." |
| "This organization can't use PostHog Code." | "Edit the template's file in its repository, as its `change_prompt_context` describes." |
| "This organization used up its PostHog Code credits." | "Edit the template's file in its repository, as its `change_prompt_context` describes. PostHog Code is available again when the credits renew." |

[PostHog AI and the Slack bot](#ask-posthog-ai-or-the-slack-bot) get the first row when they call this route, because they run inside PostHog Code. An agent that gets it doesn't retry. It gives the person the link to the template, which is the last line of the template's `change_prompt_context`.

### `posthog_code_run_failed`

`400` on a [change request](#run-with-posthog-code).

PostHog Code refused to start the task. `detail` is the reason PostHog Code gave, or "PostHog Code could not start the task." when it gave none. The API says:

- `why`: "PostHog Code refused to start the task."
- `fix`: "Fix what the detail names, then request the change again."

### `template_superseded`

A warning, not an error, in the `202` body of a send:

```json
{
  "message_id": "01a146ff-acd6-0001-cb61-b4d68ddaaed2",
  "warnings": [
    {
      "code": "template_superseded",
      "detail": "The email was sent with the template's current content, because newer content replaced the content you hold.",
      "fix": "Deploy the newer file, or upload your file to publish it again."
    }
  ]
}
```

The email went out with the template's current content, because newer content replaced the content of your file. This is normal during a [rolling deploy](#rolling-deploys).

**Fix:** The API says: "Deploy the newer file, or upload your file to publish it again." To publish your content on purpose, upload it with the [upload route](#upload-a-template-by-key), without `if_not_superseded`. In the SDKs, the warning is in the result's warnings as `{ code, message, fix }`, and the SDK logs it once.

### Errors from the SDKs

The SDKs return these codes without a call to PostHog, or when the call didn't reach PostHog or got no code back:

#### `missing_secret_key`

The client has no secret key. The SDKs report it with the name `missing_api_key`. **Fix:** Set the `secretKey` option (`secret_key` in Python) to a project secret API key with `hog_flow:write`.

#### `missing_app_host`

The client's `host` isn't PostHog Cloud, and the client has no app host, so the SDK sent nothing. The secret key never goes to a host that can be a reverse proxy for events. **Fix:** Set the `appHost` option (`app_host` in Python) to your PostHog app host, such as `https://posthog.example.com`. See [the app host](#set-up-the-client).

#### `app_host_required`

The same case as [`missing_app_host`](#missing_app_host), in the first release of `posthog-python`'s email sends. **Fix:** Set the app host, as for `missing_app_host`.

#### `client_disabled`

The client is disabled, so nothing was sent. **Fix:** Turn off the client's `disabled` option where you want to send email.

#### `network_error`

The request didn't reach PostHog, or no answer came back. The email may or may not be queued. The SDKs report it with the name `service_unavailable`, and retry with the same idempotency key, so a retry doesn't send a second email. **Fix:** Check the network and the `host` or app host option.

#### `api_error`

PostHog answered with an error that has no `code`, or with a body that the SDK can't read. The SDKs report it with the name `application_error`. **Fix:** Check the status code and the message of the error.

#### `unexpected_error`

The call failed in an unexpected way. The SDKs report it with the name `application_error`. **Fix:** Check the message of the error. If it continues, [contact us in-app](https://app.posthog.com/#panel=support%3Afeedback%3A%3Alow%3Atrue).

Before any request, posthog-node checks the form of the call, the IDs, the keys, the attachments, and the idempotency key. It checks only the types: PostHog checks the limits. A failed check sends nothing and has the name `validation_error`. Its code is [`invalid_template_key`](#invalid_template_key), [`invalid_idempotency_key`](#invalid_idempotency_key), or one of the codes below. posthog-python raises a `TypeError` or a `ValueError` for these cases instead.

#### `invalid_form`

The call passes both `templateId` and `templateKey`, or neither. The SDK says: "Send either templateId, or templateKey with subject and html or text." **Fix:** Pass `templateId` for a template made in PostHog, or `templateKey` with the content. See [how it works](#how-it-works).

#### `invalid_template_id`

The template ID isn't a UUID. The SDK says: "templateId must be the UUID of a template." **Fix:** Copy the ID from the template's **API** tab in Workflows.

#### `invalid_attachment`

`attachments` isn't a list, a file has no `content` as a `Buffer`, a `Uint8Array`, or a Base64 string, or a file has a `path`. PostHog doesn't fetch files: "PostHog can't fetch an attachment from a path or URL. Read the file and pass its content instead." **Fix:** Read the file in your code and pass its content.

#### `invalid_message_id`

The ID passed to `posthog.emails.get` is empty or isn't a string. The SDK says: "id must be the id that send returned." **Fix:** Pass the `id` that the send returned.
